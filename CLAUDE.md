# Instructions for agents working in this repository

Read `SPEC.md` in full before writing anything. Then read `TASKS.md` for the current milestone. `PLAN.md` explains why the milestones are ordered as they are. This file is the rules; the spec is the contract; where they disagree, the spec wins and this file has a bug.

## What this project is

A signed, append-only, independently verifiable decision log for systems where an LLM-driven component may *request* consequential actions but never *authorize* them, plus a test kit that runs such systems under load with scheduled faults and checks the log afterward. There is no LLM code here and no test needs a model.

## Rules that are not negotiable

1. **Fail closed, everywhere, with no exceptions and no flags.** No fallback paths. No optional checks. No configuration value that relaxes a rule. No "lenient mode." If you find yourself adding `if strict:` or `try: ... except: pass`, stop; that is a bypass token and the grep tests will reject it. A failure to log is a rejection. A failure to verify is a rejection. A timeout is a rejection.
2. **Tests first, from the invariants table (SPEC §7).** Each PR adds the positive pinning test, the mechanism, and the mutation diff under `mutations/` in the same change. A mutation diff deletes or disables the mechanism; CI applies it in a throwaway checkout and asserts the suite goes red.
3. **Never touch `spec/vectors/`, `spec/vectors.sha256`, or any key material.** Vectors are generated by `tools/vectors-go`, which is not the code under test. If the Python disagrees with a vector, the Python is wrong. A vector change requires a spec version bump by a human.
4. **The verifier (`packages/audittrail-verify`, import root `audittrail_verify`) imports nothing from `audittrail`.** Not a helper, not a schema loader, not a test fixture. Its tests read committed files under `spec/` only. Canonicalization is deliberately implemented twice; the vectors and a property test keep the copies honest.
5. **The on-disk line is the canonical bytes.** Every reader checks `line == JCS(parse(line))` byte for byte before trusting anything in it. Never normalize, never "clean up," never accept close enough.
6. **No text channel.** Every string field in a record is validated against the regex or enum in SPEC §3.1 at construction. There is no field that can hold free text, and no function in `audittrail` accepts arbitrary text as a parameter.
7. **No clever code.** If a reviewer cannot explain a function in one sentence, it is rewritten. Clever is treated as malicious. No metaphors in identifiers; `Receipt`, `Log`, `verify`.
8. **Dependencies are pinned and reviewed.** Do not add a dependency without stating in the PR what it does and why the standard library cannot. The verifier should have at most: a JCS implementation, an Ed25519 implementation, and nothing else.
9. **One open PR at a time.** Finish, get it merged, then start the next.
10. **This repository contains nothing derived from any employer's systems.** No system names, field names, counterparties, ticket text, or latency traces from anything but this repository's own synthetic data. The PR template asks; answer it honestly.

## How to work a task

- Open `TASKS.md`, take the first unchecked item in the current milestone, and do only that.
- Write the failing test. Make it pass. Write the mutation diff. Run `make check` (lint, types, tests, mutations, grep tests). Open the PR with the template filled in.
- Docstrings say what a function does **not** do. `interrogate --fail-under 100` enforces presence; the reviewer enforces content.
- Do not refactor adjacent code. Do not "improve" the spec. If the spec is wrong, open an issue quoting the section and stop.

## Things agents do by reflex that are forbidden here

- Adding a `verify=False`, `strict=False`, `allow_*`, or `skip_*` parameter. Forbidden.
- Catching a broad exception and continuing. Forbidden. Catch narrowly, re-raise as the typed error, and the caller rejects.
- Writing a helper that "parses leniently" for convenience in tests. Forbidden; tests use the strict parser or committed fixtures.
- Generating test keys or vectors in Python "to save time." Forbidden; see rule 3.
- Pulling in `pydantic`, `attrs`, `orjson`, or any serializer with its own ideas about canonical form. Forbidden in the trust path.
- Marking a flaky test as `xfail` or adding retries. Forbidden; a flaky test in this repository is a bug in the code under test until proven otherwise.

## Layout

```
packages/audittrail-log/       library (import root: audittrail)
packages/audittrail-verify/    verifier + reconciler CLI (import root: audittrail_verify)
packages/audittrail-testkit/   mock model, oracle stub, harness, conformance (import root: audittrail_testkit)
apps/gate-stub/  apps/consumer-stub/  apps/gate-stub-go/
tools/vectors-go/  tools/anchors-pull/
spec/            the contract: schema, reasons, keyring example, vectors (+ manifest)
mutations/       I*.diff
deploy/          compose, hardening, schedules
```

## Definition of done

Positive test passes; mutation diff applies to HEAD and turns CI red; `make check` is green; docstring gate passes; PR template answered; nothing in the change requires having seen a system outside this repository to understand.
